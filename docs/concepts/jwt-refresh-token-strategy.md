# Token storage strategy: in-memory access token + rotating opaque refresh cookie vs. the alternatives

## The criteria that actually matter for this decision

Auth token storage is one of the most heavily interview-probed areas of backend design, and for good reason — nearly every plausible-looking option has a real, specific attack it fails to. The criteria aren't abstract "security best practices"; they're the concrete properties that determine which attack surface each option leaves open:

- **What can a script running on the page (XSS) read?** Any credential a malicious or compromised script can read, it can exfiltrate — full stop. The question is never "could XSS happen," it's "if it does, what does the attacker walk away with."
- **What does the browser attach automatically to a request, regardless of which site triggered it?** Cookies ride along with any request to their origin unless explicitly told not to — that's the mechanism CSRF exploits, and it's orthogonal to XSS.
- **If a credential is captured, is it immediately usable, or does the attacker still need something they don't have?** A bearer token that's just a string is game over the moment it's read. A credential that requires a server-side secret to redeem is not.
- **How long does a leaked credential stay valid, regardless of how it leaked?** Every mitigation above is defense against a *specific* leak vector; TTL is defense against *all of them at once*, including ones nobody has thought of yet.
- **Can token theft be detected after the fact, not just prevented in advance?** Prevention fails sometimes. The design needs a second line that notices when it has.
- **The legacy app's actual failure mode**, because the whole point of an audit-driven rewrite is not repeating it: `httpOnly` was set on the cookie, but the JWT was *also* returned in the response body (defeating the point of `httpOnly`), no `Secure` or `SameSite` flags were set, and logout was a `GET` — meaning any page on the internet could log a user out via `<img src="…/logout">`. See [`L-10`](../legacy-audit.md#l-10).

## Comparison at a glance

| Criterion | JWT in `localStorage` | JWT in an `HttpOnly` cookie, API authenticates from it | Chosen: in-memory access token + opaque rotating refresh cookie |
|---|---|---|---|
| Readable by XSS? | Yes — `localStorage` is plain JS-accessible storage | No — `HttpOnly` blocks `document.cookie`/JS access | Access token: readable, but not persisted anywhere across page loads. Refresh token: no — `HttpOnly`, and opaque even if read |
| Rides along on cross-site requests automatically? | No (not a cookie, must be attached manually) | Yes, unless `SameSite` stops it — CSRF surface | Refresh cookie is `SameSite=Strict` and scoped to `Path=/api/auth` — doesn't ride along cross-site or to unrelated endpoints |
| Is the captured value itself usable as a credential? | Yes — a JWT is fully self-contained and bearer-valid | Yes — same JWT problem, just relocated | Access token yes (bounded by 15 min TTL); refresh token no — opaque and hashed server-side, possession of the raw value alone doesn't forge anything without the hash matching |
| Requires its own separate mitigation layer? | No extra layer, but no defense against XSS either | Yes — CSRF tokens or double-submit cookie, extra complexity | No extra layer needed — the design itself closes both surfaces |
| Theft detectable after the fact? | No | No | Yes — reuse detection on rotation |
| Blast radius if leaked anyway | Full token lifetime (commonly hours) | Full token lifetime | Access token: ≤15 min. Refresh token: caught on next legitimate use via reuse detection, whole family revoked |

## Why not each alternative — the technical case

### JWT in `localStorage`

The default a huge number of tutorials teach, which is exactly why it's worth being precise about why it's wrong here.

- `localStorage` has no access restriction beyond same-origin — any JavaScript executing on the page, in any context, can read it with `localStorage.getItem(...)`. There is no `HttpOnly`-equivalent flag for `localStorage`; the storage API was never designed to hold secrets.
- This matters even for a React app with React's default JSX-escaping XSS protections, because those protections cover exactly one injection vector (interpolating untrusted strings into JSX) and there are several others that don't go through it at all: a single `dangerouslySetInnerHTML` call rendering user-generated content (a product review, a store name) without sanitization; a vulnerable transitive npm dependency executing arbitrary code in the page context, which has happened repeatedly in real supply-chain incidents; or stored XSS in any user-generated content field that later gets rendered somewhere React's escaping doesn't reach (e.g. an `href`, a dynamically constructed URL, a third-party widget). "We use React" is not an XSS immunity — it just narrows which mistake has to happen.
- Once read, a JWT is a complete, self-contained bearer credential — whoever has the string can present it as-is to the API and be authenticated as the user, with no further secret needed. There is nothing to "unlock"; the token itself is the whole answer.
- **Where it would have won:** genuine operational simplicity — no separate refresh flow, no cookie configuration, works identically across native mobile clients that don't have first-class cookie jars. That's a real advantage for certain client shapes (a mobile app talking to the same API), just not for a browser-based SPA, which is what this project is.

### JWT in an `HttpOnly` cookie the API reads directly for authentication

The trap option — it looks like the fix for the `localStorage` problem, and it does fix *that specific* problem, while opening a different one.

- `HttpOnly` genuinely stops `document.cookie` and `localStorage`-style JS access, so an XSS payload cannot read the token value directly. This is real progress over the previous option — worth saying plainly rather than dismissing.
- But a cookie is attached by the browser to **every** request to its origin, automatically, regardless of what page or site triggered that request — that's the entire CSRF attack surface in one sentence. Concretely: a user is logged into the grocery app in one tab; they visit `evil.com` in another tab; a form on `evil.com` auto-submits `POST https://groceryeasy.example/api/orders` (or an `<img src="…">` for a `GET`-based state change, which is exactly what the legacy app's logout endpoint allowed, [`L-10`](../legacy-audit.md#l-10)). The browser attaches the `HttpOnly` cookie to that request because it's addressed to the grocery API's origin — the browser has no way to know the *request* originated from a hostile page rather than the app's own UI. If the API authenticates purely from "a valid cookie was present," that forged request succeeds as the logged-in user, and the attacker never needed to read the token at all.
- The fix for CSRF is well understood — `SameSite=Strict/Lax`, CSRF tokens, or the double-submit cookie pattern — but it is a **second, separate mechanism** that has to be designed, implemented, and kept correct on every state-changing endpoint. "The API trusts a cookie for authentication" reopens exactly the problem `HttpOnly` looked like it had closed; you've traded an XSS-readable token for a forgeable request, and now need to spend real engineering effort re-closing that gap.
- **Where it would have won:** if the API is *only* ever called from the app's own frontend and never needs to distinguish "this request came from my UI" from "this request came from anywhere," and `SameSite=Strict` alone is judged sufficient — which is close to true for a same-site SPA, but "close to true" is exactly the kind of gap that's expensive to get wrong, and it's still one more thing to verify on every endpoint rather than something structurally impossible.

### The chosen design: 15-minute in-memory access token + opaque, hashed, narrowly-scoped refresh cookie

The access token is a short-lived JWT held **only in application memory** (Redux state) — never written to `localStorage`, `sessionStorage`, or a cookie, so it exists only as long as the tab's JavaScript runtime does and vanishes on a hard refresh (the accepted cost — see below). The refresh token is a **separate, opaque 256-bit random value** — not a JWT, carries no claims, no information can be extracted from it by inspection — stored **hashed** server-side (so even a database read doesn't yield a usable credential) and delivered as a cookie scoped with `HttpOnly; Secure; SameSite=Strict; Path=/api/auth`.

Precisely why this closes both attack surfaces at once:

- **Against XSS:** the access token is never persisted anywhere a script can read across page loads — it lives in memory for the current tab session only. Even in the worst case where an XSS payload does manage to read it out of running application state (a real risk this design doesn't claim to eliminate — more on that below), the token is only useful for the remainder of its 15-minute lifetime. There is no long-lived bearer credential sitting in a storage API waiting to be read at leisure.
- **Against CSRF on the refresh flow:** `SameSite=Strict` means the cookie is not attached to any request that originates from a different site at all — not even top-level navigation from an external link, which `Lax` would still allow. `Path=/api/auth` means the cookie isn't even sent to the rest of the API surface; it only ever rides along on requests to the auth endpoints that actually need it, shrinking the set of endpoints that have to reason about it to just those addresses. So a forged cross-site request the way the CSRF-cookie scenario above described simply never carries this cookie in the first place.
- **Even in a scenario where the refresh cookie is somehow read anyway** (a browser/OS-level compromise, a misconfigured proxy logging cookies, physical device access) — the value is opaque and meaningless on inspection, and the server stores only its hash. Possessing the raw cookie value is necessary but the server-side comparison is what actually authenticates it; nothing about the refresh token is a self-contained, forge-once-use-anywhere bearer credential the way a raw JWT is. This is the same principle as never storing plaintext passwords, applied to a long-lived credential instead of a short-lived one.

### Rotation with reuse detection, as its own sub-topic

**What it is:** every time a refresh token is used to obtain a new access token, the server issues a **brand-new** refresh token and marks the presented one as *replaced* (not merely deleted — the record persists so a later presentation of it can be recognized). The client is expected to always hold only the newest token in the chain — the "family." If the server ever receives a refresh token that has already been marked replaced, that is not a normal error, it is **proof of leakage**: the only way an already-rotated token gets presented again is if a copy of it exists somewhere other than the legitimate client, because the legitimate client overwrote its copy with the new one the moment rotation happened. The server's response to that signal is to revoke the **entire token family** — every token descended from that original login — and log a security event, so a single leaked-and-detected token can't be quietly re-exploited via some other still-valid descendant.

**Why this specifically catches a scenario plain rotation (without reuse detection) misses:** imagine an attacker steals a refresh token — through a network capture, a compromised dependency, a leaked log line — and uses it once, before the legitimate user's next refresh. With **plain rotation and no reuse tracking**, the attacker's use is indistinguishable from a normal refresh: the server issues a new token to whoever presented the valid old one, no error occurs, nothing looks wrong. The legitimate user's *next* refresh attempt then fails (their token is now stale, since the attacker's request already rotated it) — which most implementations would treat as "just log the user out and reauth," silently swallowing the fact that a theft happened at all. **With reuse detection**, the moment *either* party presents a token that's already been superseded, the linear lineage check catches it, because reuse detection isn't asking "is this token valid" (both the attacker's stolen copy and a hypothetical still-fresh token would pass that check) — it's asking "has this specific token already been consumed by someone," which only the *out-of-order* presentation the theft causes triggers. The attack this specifically defeats is exactly the one that's realistic: a token captured once and reused, not an attacker continuously racing the legitimate user in real time (which is a different, harder problem this design doesn't claim to solve).

This is the direct structural answer to [`L-10`](../legacy-audit.md#l-10): the legacy app had no rotation, no reuse detection, and no `Secure`/`SameSite` flags at all — a cookie that rode along on any cross-site request, for a token that (because it was also returned in the response body) was readable by XSS anyway, backing a logout endpoint that was a bare `GET` and could be triggered by an `<img>` tag from any site on the internet. Every one of those independent gaps is closed by a different piece of this design: `SameSite=Strict` + `Path` scoping closes the CSRF surface, opacity + server-side hashing closes the "readable token" surface, and rotation + reuse detection turns "a token leaked and I'll never know" into "a token leaked and the system noticed and revoked the whole family."

### Why the access token is short-lived at all, given it's already in-memory-only

This is worth answering directly because it's the question most likely to expose hand-waving: if the access token never touches persistent storage, why does its lifetime matter?

**Defense in depth — the TTL is not defending against the storage mechanism, it's defending against everything else.** "In memory" describes *where the token normally lives*, not a guarantee that nothing can ever read application memory. Concrete leak vectors that have nothing to do with `localStorage` vs. cookies at all:

- A **memory-inspection attack** — a browser extension with broad permissions, a compromised dev tools session, or a debugging/profiling tool with access to the running page's heap can read variables out of live application state, Redux store included.
- A **malicious or compromised browser extension** — extensions routinely have permission to read page content and execute in page context; a supply-chain-compromised extension (a real, recurring category of incident) can read anything the page can read, including in-memory state, without ever touching `localStorage`.
- A **supply-chain-compromised npm dependency** — the same category of risk that makes `localStorage` unsafe under XSS applies to in-memory state too, if the compromised code runs in the same JS context as the app (which most dependencies do). "In memory, not `localStorage`" narrows the read surface; it does not eliminate it, because anything with code-execution in the page can, in principle, walk the same object graph the app itself uses.

None of these are prevented by choosing memory over `localStorage` — they're prevented, or rather *bounded*, by the token simply not being valid for very long. A 15-minute TTL means that whichever of these unlikely-but-real vectors eventually causes a leak, the attacker's window is 15 minutes, not the token's full session lifetime. This is the same reasoning that justifies short-lived credentials generally: you can't enumerate every way a secret might leak in advance, so the mitigation that works against all of them at once is making the secret stop being useful quickly. The refresh token is the mechanism that makes a short access-token TTL *usable* without forcing the user to re-enter a password every 15 minutes — the access token's short life is the security property, and the refresh flow is what makes that property free from a UX standpoint.

## Interview questions

**Q: Why not just put the JWT in an `HttpOnly` cookie and let the API authenticate off it — doesn't that solve the XSS problem?**
It solves XSS specifically, but it reopens CSRF: cookies are attached by the browser to any request addressed to their origin, regardless of which site or page triggered the request. A hostile page can make the browser send an authenticated request to the API without ever reading the cookie's contents — it doesn't need to, the browser attaches it automatically. Fixing that requires a second mechanism (CSRF tokens, double-submit cookie, strict `SameSite`), which is extra complexity layered on top rather than a problem this option avoided.

**Q: If the access token is already only in memory, why does it still need a short TTL — isn't that redundant?**
No, because "in memory" only describes the normal storage location, not an absolute guarantee against every read vector. A malicious browser extension, a memory-inspection tool, or a supply-chain-compromised dependency executing in the page's own JS context can all read live application state without ever touching `localStorage`. The short TTL is defense in depth — it bounds the blast radius of *any* leak vector, including ones this design doesn't specifically anticipate, rather than relying on the storage choice to be the only line of defense.

**Q: What's the difference between rotation and rotation-with-reuse-detection — isn't plain rotation enough?**
Plain rotation limits how long a stolen refresh token stays useful, but if an attacker uses a stolen token exactly once, before the legitimate user's next refresh, nothing about plain rotation notices — the server just sees a valid token and issues a new one, same as any legitimate refresh. Reuse detection adds a check for whether a *specific* token has already been consumed once; since the legitimate client always overwrites its copy on rotation, a second presentation of an already-rotated token can only mean a leaked copy exists elsewhere. That's the signal that triggers revoking the whole token family, and it's exactly the scenario plain rotation is blind to.

**Q: Why is the refresh token opaque instead of also a JWT?**
Two reasons. First, it carries no information by design — a JWT's claims are base64-encoded, not encrypted, so anyone who reads a JWT refresh token can see everything in it even before verifying the signature; an opaque random value reveals nothing on inspection. Second, and more important, it's stored hashed server-side, so validating it requires a database lookup and hash comparison — there's no way to "verify" it offline the way a JWT's signature can be checked without hitting the database. That tradeoff (an extra DB round-trip per refresh) buys the ability to actually revoke it instantly and to detect reuse, neither of which a self-contained, stateless JWT refresh token could do without maintaining the same kind of server-side state anyway — at which point it wouldn't really be stateless.

**Q: Concretely, what did the legacy app get wrong here, and which part of this design fixes which part of it?**
Three independent failures stacked in one implementation: no `Secure`/`SameSite` flags (fixed here by `Secure; SameSite=Strict`), the JWT returned in the response body in addition to the cookie so XSS could read it regardless of `HttpOnly` (fixed by never persisting the access token anywhere and keeping it short-lived), and logout implemented as a bare `GET` so any page on the internet could trigger it via `<img src>` (fixed structurally — no state-changing endpoint in this design is reachable by a simple cross-origin `GET`, and the refresh cookie's `SameSite=Strict` plus path scoping means it isn't even attached to a cross-site request in the first place).

**Q: What's the actual cost of this design compared to just using `localStorage`?**
A hard page refresh loses the in-memory access token, so the app has to do a silent refresh round-trip against the auth endpoint before the first request after any hard reload — `localStorage` wouldn't need that, since the token would just still be sitting there. That's a real, accepted UX cost, traded for the access token never being a persistent, XSS-readable bearer credential.
